TSIS 5 — Project Charter & Force Field Analysis (3 pts)

Launch meeting

Kick-off before detailed planning; senior manager present = top-management commitment (sponsor = instructor). Outputs: technical scope (not final), accepted responsibilities, tentative dates, start of risk thinking.
16 Sep 2026; roles split; Agile, 1-week sprints; MVP boundary agreed.

Project Charter

Formal document that authorizes the project and the PM's authority to direct work, spend, request resources. After approval, significant scope changes need a written change order. Charter ≠ project plan ≠ sprint backlog — it is the baseline authorization; WBS/backlog come later (§6.2).

Our scope & risks

Must (MVP): login/auth, join building by flat code, emergency & outage alerts, complaints/requests with status history, residential news/building channel, community voting, multilingual UI.
Out of scope: payment/bank integration (only Kaspi transfer + manager phone + receipt upload), native mobile app, analytics dashboard (low). Resident chat → next sprint.
Risks: AI-token shortage · frontend–backend integration (medium, manageable) · 2-person team / absence · scope creep · exam load.

Scope creep

Uncontrolled scope growth. Case: UK Child Support Agency — £456M lost, 2,500 unmanaged change requests. "If it's not in prod, it shouldn't be in the spec (TZ)" — removed payment mentions to avoid contradiction.

Force Field Analysis (Kurt Lewin)

Central MVP statement; driving forces (+) vs restraining forces (−), strength 1–5; ≥4 + ≥4; ≥3 actions (owner + week). Either strengthen a driver or weaken a restraint. If restraints dominate → narrow objectives, no heroic charter. Slides: "Power Field" = political feasibility (stakeholders, influence, stance).

WBS & baseline

WBS: project → major activities → tasks → subtasks → work packages (owner, budget, duration, predecessors). Rules: consistent granularity, delegate downward, sign-off, rolling-wave planning (detail near-term now). Baseline = signed-off plan; changes only via change order. Flow: Launch → Charter → WBS → Baseline.

Scrum basics

PO owns/prioritizes backlog · Scrum Master removes impediments · Dev Team self-organizing, cross-functional. Events: Sprint, Sprint Planning, Daily Scrum (15 min), Review + Retro. Artifacts: Product Backlog → Sprint Backlog → Increment.

TSIS 6 — User Stories & Profit Forecast (4 pts)

User story

As a [user], I want [action], so that [benefit]. User's view, not a tech spec — a conversation starter. Done when the user completes the scenario, not when code compiles. Features list = what the system does; stories = value for a user.

Acceptance criteria — GWT

Given context · When action · Then observable yes/no outcome.
Given I'm a logged-in resident, When the manager posts a gas-outage alert, Then I see it pinned at the top of my feed.

INVEST

Independent · Negotiable · Valuable · Estimable · Small (one sprint) · Testable. Fails → rewrite before grooming.

MoSCoW

Must · Should · Could · Won't (drop). Rule: 8–12 stories, ≥6 Must, ≤2 Should, stable IDs US-01…

Backlog grooming (refinement)

PO-led, before Sprint Planning. Understand it? (no → rewrite) · In scope? (no → park) · Small enough? (no → split) → ready backlog / Definition of Ready. Backlog pyramid: top 10–15 fully detailed + estimated; middle T-shirt sizes (S/M/L/XL); tail = titles only. Student cadence 30–45 min weekly.
Decisions: one group chat per residential complex; payments out of MVP.

Profit forecast

Net value = benefit − cost over 12 months, Base / Pessimistic / Optimistic. ≥5 explicit assumptions (users, usage, time saved, cost…), ≥2 change between scenarios. Feeds the charter's Business Case. Be ready: which assumptions changed, why pessimistic is still positive / what you'd cut.

TSIS 7 — Release Plan, Budget & Sprint Backlog (4 pts)

Story points (SP)

Relative effort = complexity + uncertainty + volume. Not hours, not money; team-relative. Fibonacci 1-2-3-5-8-13-21 (gaps grow with uncertainty). Target 3–5; 8 = warning (split?); 13 = not understood → split or spike (time-boxed research). Value of estimating = shared understanding.

Planning poker

PO reads story → each picks card face down → reveal simultaneously (avoids anchoring bias) → highest & lowest explain → re-vote until convergence (2–3 rounds). Never average. Disagreement = hidden assumptions.

Three backlogs

ArtifactQuestionOwner
Product BacklogWhat could we build?PO
Release / MVP planWhat ships by deadline?PO + team
Sprint BacklogWhat do we finish this sprint?Dev team
Flow: Features → Stories → Groomed Backlog → Release Plan → Sprint Backlog → Working Software.

Release planning & prioritization

R1 = MVP (Must only, demo-able) · R2 = Should + polish, if time allows. Inputs: charter goals, Must stories, real hours/sprint. Prioritize by MoSCoW, value vs cost, risk (unknowns early), dependencies (auth first). PO decides, team informs. Anti-pattern: priority by who shouted loudest.

Estimate levels: rough/order-of-magnitude → budget estimate (SP live here) → definitive (work packages known).
Contingency (§7.3): visible reserve for risk, not padding; keep known costs separate from risk costs.
Cone of uncertainty: earlier = less known → refine every sprint, re-baseline openly. Cases: "Estimates That Lied" (guess treated as contract); Limerick nuclear plant under budget via continuous refinement.
Consistency: hours & user counts in budget = profit forecast.

Sprint backlog (output of Sprint Planning)

Sprint Goal (one sentence) + selected PBIs (Product Backlog Items) with SP + ≥3 tasks per PBI (design, code, test, docs) with owner.
"A resident can join their building by flat code, log in, and see emergency/outage alerts."

Likely trick questions

Charter vs plan vs backlog?Charter authorizes; WBS/plan details the work; backlog drives sprints.
Why not hours for SP?Relative sizing is faster and honest under uncertainty; hours appear at task level in the sprint backlog.
Someone wants payments mid-sprint?Change procedure (Resources): PM + sponsor approve in writing; otherwise parked for R2.
Profit vs budget?Budget = cost to build; profit forecast = net value (benefit − cost) after launch, 3 scenarios.
Why hybrid?Fixed TSIS deadlines = plan-driven gates; inside them 1-week Scrum sprints.
Grooming vs Sprint Planning?Grooming clarifies/sizes stories ahead; Sprint Planning commits a goal + PBIs + tasks for this sprint.
Who prioritizes?Product Owner; team informs feasibility and owns capacity.
Restraints dominate the force field?Act on the strongest restraint; if not mitigable, narrow charter objectives.
